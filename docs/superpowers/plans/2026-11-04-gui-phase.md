# The GUI phase: the sampler's surface and the modulation screen — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the sampler the controls its landed DSP deserves, and move the modulation system's full interface to a screen of its own so the instrument screen can show the instrument.

**Architecture:** The modulation screen is a full-graph layer pushed over the instrument screen, with two panes — the source list on the left, the selected source's parameters and routes on the right. The instrument screen keeps a single one-line modulation slot that cycles through the connected modulators, and the sampler's control panel grows two rows into the space the list gives up. The sampler's character panel binds the chain's existing parameters; the OTA cascade and the crossfade land behind the filter and loop controls that are currently inert.

**Tech Stack:** C11, raylib 5.5 (the vendored copy), PortAudio, Unity (the test framework), Meson + Ninja, TOML/JSON for the device profiles, `kissfft` (vendored).

**Spec:** `docs/superpowers/specs/2026-11-04-gui-phase-design.md` — the plan argues from the spec, so the spec travels with it; executors read both.

**Sibling documents:** `docs/superpowers/plans/2026-11-02-adaptive-arm-handheld.md` (the canonical-core plan), `docs/superpowers/plans/2026-10-09-sampler-emulation-engine.md` (the character-engine plan), `docs/superpowers/plans/2026-10-09-sampler-emulation-engine-progress.md` (its ledger), `docs/superpowers/specs/2026-11-03-canonical-synthesis-spec.md` (the synthesis contract).

## Global Constraints

These apply to every task. They are the spec's project-wide requirements, copied with their exact values.

- **Criterion C.** No synthesis operation may depend on the device, the architecture, the voice count, the channel count or the load. A voice's samples are a pure function of its settings and the song.
- **The canonical engine rate.** `SPECTRAX_ENGINE_RATE` is 48000 and is a compile-time constant. No synthesis path may read a runtime rate.
- **The no-libm invariant.** Nothing on the audio path, nor in the bake, may call an inexact libm transcendental. The only sources of trigonometry, exponentials, logarithms, powers and the one-pole coefficient are `src/canonical_math.{c,h}`: `canonicalSin`, `canonicalCos`, `canonicalExp`, `canonicalLog`, `canonicalPow`, `canonicalOnePoleCoef(fc, sr)`. The lint's file list lives in `tests/dsp/test_canonical_math.c` and covers the whole audio path plus the bake; a new audio-path file must be added to it.
- **Strict floating point.** `-ffast-math` is forbidden; `-ffp-contract=off` is on for the whole project. A new file inherits it — do not add a file-scoped override.
- **No mouse.** The app has no pointer input and this phase adds none. Every interaction uses the app's verbs: `LEFT`, `RIGHT`, `UP`, `DOWN`, `SELECT`, `START`, `EDIT`, `FUNCTION`, `NAV_LEFT`, `NAV_RIGHT`, `MOD_EXTRA`, `ADD`, `REMOVE`, `CTRL`, `SHIFT`, `EQUAL`, `MINUS`.
- **The app's idioms.** Dials turn with `LEFT`/`RIGHT`; action buttons fire on `EDIT`; the arrows move the cursor between nodes; `FUNCTION`+arrows is page navigation; `SELECT`+`UP`/`DOWN` cycles the instrument screen's channel; `SELECT`+`LEFT`/`RIGHT` is the global scene switch; `NAV_LEFT`/`NAV_RIGHT` (L1/R1 on a gamepad, Q/W on the keyboard) are the fine step. On the keyboard `SHIFT` *is* `SELECT` (both are `KEY_LEFT_SHIFT`, `input.h:45,55`) and `CTRL` *is* `MOD_EXTRA` (`input.h:51,54`) — never bind a new chord to `SHIFT` or `CTRL` without checking that collision.
- **Parameter discipline.** A parameter cleared by a preset apply or an instrument rebuild must be recreated before the next access (memory #1135). Every new parameter is created with its range, step and default, and appears in the preset format.
- **The preset format bumps to V5** (`IPB5`) for the crossfade, with a V4→V5 migration. The format is a raw struct dump; the migration pattern is a legacy struct definition in `src/io/preset_io.c` plus a field-by-field copy, exactly as `PresetV3`/`SamplerPatchV3` do for V4.
- **The layout's named layouts live in `src/layout.json`** (`mod-source-row`, `mod-source-row-core`, `fm-op-row`, `env-stage`). A new row layout is added there by name and applied with `applyLayout(node, "name")`.
- **The coverage floors live in `meson/coverage-min.txt`** as branch percentages, and they only ever go up. A new module is listed at its measured level when it lands, and raised as its tests grow.
- **The tests are Unity** (`tests/unity.h`), registered in `tests/meson.build`; a GUI test links `gui_test_libs`; a test needing the repo's path takes `-DSPECTRAX_SRC_DIR=` or `-DSPECTRAX_REPO_ROOT=`.
- **The harness** is `src/tools/instrument_harness/`; a scripted fixture is `src/tools/instrument_harness/fixtures/<name>.txt`, run with `bash src/tools/instrument_harness/run_scripted.sh fixtures/<name>.txt` from the repo root after `meson install -C build`.
- **Docs live under `docs/`, which is git-ignored** — add them with `git add -f`.
- **The tracked binaries in `bin/` are rebuilt and committed with every task.** `bin/spectrax`, `bin/instrument_harness` and `bin/spectrax_bench` are tracked in git and every commit in the branch's history carries the rebuilt copies — the harness runs from `bin/`, so a stale binary means a stale test. Each task: `meson install -C build`, then `git add bin/` in the same commit as the source change.

## Review Focus

The five input classes or failure modes the spec implies that no task's tests would otherwise exercise, most likely to bite a person first.

1. **A crossfade longer than the loop.** The user drags the loop's end close to its start and then turns the crossfade up. The crossfade must be clamped to the loop's length, or the read runs past the buffer.
2. **A loop whose start is at or past its end.** The points can be moved independently, so this state is reachable. The loop region must be normalised or rejected, never read backwards.
3. **A preset saved before the crossfade existed.** A V4 file opens in a V5 build. The migration must produce a sane crossfade (zero), not a garbage length.
4. **A step whose velocity is zero.** Zero means *unset*, so it plays at full. A lane that draws it as silence, or a lane that lets it be edited to a value that is not 1..127, breaks the sequencer's contract.
5. **An instrument asking for more voices than the device's budget allows.** The `VOICES` dial's value must clamp to the budget, and the user must be able to see that it did.

Each line above gets its test in the task that owns the code: 1 and 3 in Task 7, 2 in Task 8, 4 in Task 10, 5 in Task 11.

## The order, and why

The modulation list must leave the instrument screen before the sampler's panel can grow into its space, so the modulation screen is built **first, additively**, with the instrument screen's list still in place. The subtraction — removing the list — happens **last in that workstream**, on a screen that is already known-good, and it is the only irreversible-feeling step in the phase. Everything after it works in the space it frees.

The workstreams are independently shippable, so a checkpoint after any of them is a safe stopping point:

1. **The modulation screen** (Tasks 1–3) — the new screen, its layer, the picker. The instrument screen is untouched.
2. **The modulation line** (Task 4) — the line, then the list's removal, then the route lines.
3. **The sampler's character** (Tasks 5–9) — the panel, the filter, the crossfade, the points, the modes and the preview.
4. **The pattern screen and the budget** (Tasks 10–11) — independent of the above.

for i in 0..3: z[i] += g * (y - z[i]); y = z[i]

out = y

/* src/sampler_crossfade.h */
/* The fade law for a loop's crossfade.
 *
 * `correlated` is true when the loop's head and tail are the same
 * waveform (a sustained tone): the fades are equal-gain, so the two
 * copies sum to unity where they overlap. Otherwise (a drum hit, noise)
 * the fades are equal-power, so the sum's power is constant. */
typedef enum { XF_EQUAL_GAIN, XF_EQUAL_POWER } SamplerFadeLaw;

/* Measure the correlation of the loop's head and tail. The caller passes
 * the head's and the tail's sample counts in frames; the result is in
 * -1..1. */
float samplerCrossfadeCorrelation(const BakedSample *b, int loopStart, int loopEnd, int frames);

/* The law for a loop, from its measured correlation. A correlation above
 * 0.5 is correlated material. */
SamplerFadeLaw samplerCrossfadeLaw(float correlation);

/* The mix of the two copies at the seam. `phase` is 0..1 across the
 * crossfade region; `outgoing` is the copy leaving, `incoming` the one
 * arriving. */
float samplerCrossfadeMix(float outgoing, float incoming, float phase, SamplerFadeLaw law);
